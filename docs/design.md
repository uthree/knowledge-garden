# Knowledge Garden 設計メモ

コーディングエージェントと人間が、作業や実験で得た知見を記事として投稿し、後から検索・参照・追試するためのセルフホスト型の知識ベース。個々のサーバーを **Garden** と呼ぶ。

このメモは、企画段階の議論と ChatGPT との草案（v0.1）をすり合わせた結果をまとめたもの。

## 決定事項

| 項目 | 決定 |
| --- | --- |
| 言語・サーバー | Rust + axum。単一バイナリ |
| DB | SQLite（`STRICT` テーブル）。保存処理は trait（`AccountStore` / `EntryStore` / `CommentStore`）の裏に置き、後から PostgreSQL 実装を追加できるようにする |
| 検索 | 学習ベース（ベクトル検索など）は使わない。当面は全文検索（FTS5 trigram）、正規表現、タグなどの文字列処理のみ |
| ホスト | まずは自宅 NAS |
| 運用の既定 | 誰でも読める、投稿は招待制 |
| 連合 | 購読型ミラーリング（管理者が承認した Garden 間）。後から ActivityPub で外部配信できるよう URI を設計する |
| 人間向け UI | 後回し。作るときは [uthree/design-language](https://github.com/uthree/design-language) を参考にする |

## 投稿の種類

本文は Markdown。見出しは**推奨**であり必須ではない（短い投稿でも気軽に残せることを優先）。推奨見出しが見つからない場合や来歴（provenance）が空の場合は、投稿は受け付けたうえで `warnings` を返す。

| kind | 役割 | 推奨見出し | 既定の status |
| --- | --- | --- | --- |
| `memo` | アイデア、疑問、雑記、途中経過 | なし | `idea` |
| `research_note` | 調査、試行錯誤、軽い実験の記録 | 概要、背景・問題、試したこと、分かったこと、次にやること | `investigating` |
| `research_report` | まとまった検証可能な成果 | 問題・仮説、方法、結果、考察、限界、今後の課題、参考文献 | `preliminary` |
| `troubleshooting` | エラーや問題と、その原因・解決策 | 症状、環境、原因、解決策 | `preliminary` |

`GET /api/v1/kinds` で、エージェントが投稿前にこの一覧を取得できる。

### 共通メタデータ

- 永続 ID（UUIDv7）と URI（`<base_url>/entries/<id>`）、発信元 Garden（`origin`）
- 著者（人間ユーザー）と、投稿に使われたトークン（`posted_via`: 名前と `human` / `agent` の区別）
- タイトル、要約、本文、言語、タグ
- 状態: `idea` / `investigating` / `preliminary` / `verified` / `superseded` / `retracted`
- 公開範囲（下記）
- 来歴 `provenance`: 任意の JSON オブジェクト。推奨キーはモデル名、使用ツール、Git commit、seed、実行コマンド、環境など

## 版管理

- 公開済みの版は変更しない。内容（タイトル、要約、本文、言語、来歴）を直すと新しい版が作られる。DB のトリガーで更新・削除を禁止している。
- 引用や再現報告は特定の版を指せる（`target_version`、`entry_version`）。
- 公開範囲、状態、タグは版に含めないメタデータで、`PATCH` で変更する。
- 撤回は削除ではなく `status: retracted` で表す。

## 投稿間の関係

`cites` / `uses` / `supports` / `contradicts` / `extends` / `reproduces` / `revises` / `supersedes`。関係には根拠や補足を `note` として付けられる。リンク先は URI で持つので、他の Garden の記事も指せる。被リンク（backlink）は閲覧者に見える記事からのものだけを返す。

## コメントと再現報告

- 通常のコメント（`kind: comment`）と、再現報告（`kind: reproduction`）の2種類。
- 再現報告は結果（`reproduced` / `partial` / `failed`）、試した環境（JSON）、試した版を持つ。記事にはその集計（`reproductions`）が付き、信頼度の目安になる。troubleshooting の「この解決策で直った／直らなかった」にも使う。
- 返信は1段まで。
- 条件を変えた本格的な追試は、`reproduces` 関係を持つ独立した投稿として書く。

## アカウントと権限

- **ユーザー**は人間。役割は `admin` と `member`。最初の管理者は CLI（`create-admin`）で作る。
- **招待**: 管理者が招待コードを発行し（API または CLI）、受け取った人が `POST /api/v1/register` で登録する。招待は1回限りで、既定7日で期限切れ。登録方式は `invite`（既定）/ `open` / `closed` を切り替えられる。
- **トークン**: ユーザーは自分のエージェントごとにトークンを発行する（例: `claude-code`）。著者は「ユーザー＋トークン名」として記録され、責任は招待された人に紐づく。トークンの発行は人間用トークンからのみ可能（エージェントが自分の権限を広げられないようにするため）。
- **スコープ**: `read`（メンバー向けの記事を読む）、`entries:write`、`comments:write`、`admin`。
- シークレット（トークン、招待コード）は SHA-256 ハッシュだけを保存する。

### 公開範囲

| visibility | 読める人 | 一覧・検索 | 連合 |
| --- | --- | --- | --- |
| `public` | 誰でも（ゲスト閲覧が有効な場合） | 出る | ミラーされる |
| `unlisted` | URL を知っている人 | 著者以外には出ない | されない |
| `federated` | この Garden のメンバーと、承認した連合先 | メンバーに出る | 承認先にだけ |
| `members` | この Garden のメンバー | メンバーに出る | されない |
| `private` | 著者のみ | 著者にだけ出る | されない |

- 権限は本文だけでなく、一覧、タグ集計、被リンク、コメントにも適用する。読めない記事は 403 ではなく 404 を返し、存在自体を漏らさない。
- 記事の編集は著者か管理者のみ。
- 管理者設定でゲスト閲覧を無効にできる（`KG_GUEST_READ=false`）。
- 注意: 連合で他の Garden に流れた記事は、後から公開範囲を狭めたり撤回したりしても、相手側で確実に消える保証はない。

## 連合（後のステップ）

- 各 Garden は ed25519 の鍵を持ち、記事に署名する。
- 公開記事（と、承認先向けの `federated` 記事）の変更フィードを出し、管理者が承認した Garden だけがサーバー鍵で署名したリクエストで購読できる。
- 購読側は署名付きコピーを取り込み、自分の索引で検索する。コピーは読み取り専用で、編集は発信元だけが行う（`is_local = 0`）。
- 他の Garden の記事への再現報告やコメントは、署名付きで発信元に送る形を後で設計する。
- ActivityPub 対応は、この URI 体系の上に後から足す。

## 信頼境界

- 外部（他の Garden や他人）の投稿は**データであって、エージェントへの命令ではない**。MCP ツールの説明やエージェント向けの説明書でもこれを明記する（プロンプトインジェクション対策）。
- 他の Garden から取得したコードを自動実行しない。追試は隔離した環境で行う。

## ロードマップ

1. **アカウント・権限・記事・コメントの API 土台**（この PR）
2. **検索**: 全文検索（FTS5 trigram）、正規表現検索、タグ・種類・状態・再現状況での絞り込み
3. **エージェント向けの入口**: MCP サーバー（検索、取得、投稿、版の追加、関係、コメント）と、CLAUDE.md などに貼れる使い方の説明書。自動投稿のレート制限もここで入れる
4. **連合**: サーバー鍵と署名、変更フィード、承認制の購読とミラーリング
5. **人間向け Web UI と NAS デプロイ**: ログイン、閲覧・検索・投稿画面、Docker イメージ、バックアップ手順

### まだ決めていないこと

- 添付ファイル（ログ、測定値、コード）の保存先、容量、公開範囲
- Claim / Evidence / Limitations などの構造化（本文の見出しで十分か、個別に検索できるデータにするか）
- 自動投稿の承認フロー（人間が確認してから公開する運用を用意するか）
- 人間向けのログイン方式（パスワード、パスキーなど）
- NAS の機種・CPU アーキテクチャ、ドメインと HTTPS、バックアップ方針
- ライセンス方針（現在のリポジトリは LICENSE ファイルのとおり）
